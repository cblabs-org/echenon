## Test A — WiFi STA Disconnected (Designed) / Baseline Comparison (Actual)

### Design

Disconnect WiFi STA so the 2.4 GHz coexistence arbiter is not contending
with WiFi, then test whether the Android phone can connect.

### Actual execution

**Test A as designed was blocked.** When WiFi credentials are removed, the
framework enters AP-only mode and the `WiFi Station` precondition (cause=8,
severity=3) prevents `AppState::Running`. BLE init is gated behind RUNNING
state, so BLE never starts without a STA connection.

Serial evidence (AP-only boot):
```
I (2994) WifiManager: softAP('esp32-device') returned true
I (3281) Application: Precondition unsatisfied: WiFi Station (cause=8, severity=3)
  ... (repeats every 500ms, BLE never initialises)
```

> **Side-finding:** The softAP SSID uses the generic `esp32-device` instead of
> the app-configured hostname. Filed as
> [esp32-app-foundation#294](https://github.com/matthewmcneill/esp32-app-foundation/issues/294).

> **v1 finding: BLE depends on WiFi STA.** BLE cannot operate without WiFi STA.
> At boot, no STA → no RUNNING → no BLE. If STA is lost while RUNNING, the app
> regresses to CONFIGURING (`Application.cpp:471`), where BLE reconnect and
> discovery are blocked (RUNNING-only gates in `BLEManager.cpp:~855`). This
> means sustained router outage kills BLE relay even though BLE has no
> dependency on WiFi. See [v1 Finding](#v1-finding--ble-depends-on-wifi-sta)
> section below.

No `Central connected` log — the connection fails during the establishment
window. The ESP32 controller received the phone's `CONNECT_IND` and entered

failure), but heard nothing from the central in the first ~6 connection
events, causing `BLE_ERR_CONN_ESTABL_FAIL`.

### Analysis

1. **The phone is the only device that fails.** Mac and tablet connect
   reliably under identical conditions.

2. **The tablet's negotiated connection parameters** are more conservative
   than the Mac's (48.75ms interval vs 30ms; 5000ms supervision timeout
   vs 720ms). Both succeed.

3. **The phone's requested connection parameters are unknown** — the
   connection fails before the host stack logs them. HCI snoop log
   (Test C) is required to determine what the phone requested.

4. **The 0x3e failure occurs in the establishment window**, after
   `CONNECT_IND` is received. The ESP32 enters the connection but cannot
   service the first connection events — consistent with the coex arbiter
   under `WIFI_PS_NONE` not yielding WiFi radio time for BLE connection
   event servicing.

### Conclusion

Test A (WiFi off) was not executed due to the framework's BLE-requires-RUNNING
gate. The baseline comparison shows the phone fails while Mac and tablet
succeed under identical conditions. The failure is in the connection
establishment window (post-CONNECT_IND), consistent with coex starvation.
The phone's actual requested parameters are not yet known — Test C (HCI snoop)
is essential.

## Framework Coexistence Decision History

Reconstructed from PA memory files, workorders (`pr-225-ble-manager`),
source code comments, and commit messages. This is the complete record of
how the framework arrived at `PREFER_WIFI` + `WIFI_PS_NONE`.

### Timeline

#### dev.67 — First coex anomaly (WO-6 hardware acceptance, 2026-09-23)

During rapid BLE connection/disconnection cycling (3 cycles), WiFi
disconnected and fell back to AP mode:
```
wifi:Coexist: Wi-Fi connect fail, apply reconnect coex policy
```
Identified as an ESP-IDF radio coexistence limitation under connection
churn, not a logic defect.

#### dev.73–dev.80 — Radio hardening cycle (2026-09-25)

Two simultaneous failures during bench testing drove experiments:
- Android BLE connections dropped with GATT CONN TIMEOUT (Error 147/133)
- WiFi dropped with `AUTH_EXPIRE` (reason 2)

**Experiment 1: `PREFER_BT` (dev.76, commit `22882ffc`)**
- Set `esp_coex_preference_set(ESP_COEX_PREFER_BT)`
- **Result: WiFi completely starved** — HTTP portal unreachable.

**Experiment 2: `PREFER_BALANCE` (dev.78, commit `651b6eef`)**
- Set `esp_coex_preference_set(ESP_COEX_PREFER_BALANCE)`
- **Result: still caused `AUTH_EXPIRE`** during 802.11 association.
- 802.11 auth/assoc frames have a hard 1-second deadline; balanced
  time-sharing caused the WiFi radio to miss these frames.

**Decision D12: revert to `PREFER_WIFI` (dev.79, commit `7521972f`)**
- Removed `esp_coex_preference_set()` entirely, falling back to the
  ESP-IDF default (`PREFER_WIFI`, enum 0).
- WiFi auth/assoc frames granted strict arbitration priority.
- BLE stability achieved through other mechanisms:
  - Deferred connection parameter negotiation (no immediate
    `updateConnParams()` on `PeerConnected`)
  - Supervision timeout elongation (4.0s after MTU exchange)
- **This decision was codified as permanent policy:**

Source: `sdkconfig.ble.defaults` L302–315:
```ini
# IMPORTANT — do NOT call esp_coex_preference_set() in application code:
#   - PREFER_BT (dev.76):      Starved WiFi entirely — portal unreachable.
#   - PREFER_BALANCE (dev.78):  Still caused AUTH_EXPIRE during WiFi 802.11
#                               association (auth frames have a 1s deadline).
#   - Default / PREFER_WIFI:    Works reliably.  BLE stability comes from
#                               +20 dBm TX power and deferred connection
#                               parameter updates, not from coexistence tuning.
```

Source: `BLEStack.cpp` L270–273:
```cpp
// Wi-Fi / BLE coexistence: leave at ESP-IDF default (PREFER_WIFI, enum 0).
// PREFER_BT (dev.76) starved WiFi entirely; PREFER_BALANCE (dev.78) still
// caused AUTH_EXPIRE during WiFi association.
```

**STA timeout extension (dev.80, commit `1f1dd207`):**
- `STA_ATTEMPT_TIMEOUT_MS` increased from 15s → 30s to allow 802.11
  auth retry cycles (8–10s on congested 2.4 GHz) plus DHCP.

#### dev.81 — WO-10 / WIFI_PS_MIN_MODEM trial (2026-09-25)

Issue #236 addressed WiFi STA resilience. WO-10 mandated Decision **D-E**:
```cpp
void WifiManager::applyPowerSave() {
#if !defined(UNIT_TEST) && (defined(WITH_BLE) || ...)
    WiFi.setSleep(WIFI_PS_MIN_MODEM);
#else
    WiFi.setSleep(WIFI_PS_NONE);
#endif
}
```

**Rationale:** ESP-IDF logged *"Should enable WiFi modem sleep when both
WiFi and Bluetooth are enabled"*, and modem sleep was believed necessary
to yield the radio to BLE.

**The dev.81 regression:** On congested 2.4 GHz networks:
- Modem sleep caused WiFi radio to enter sleep states during 802.11 auth
  handshakes, sleeping through auth response frames
- **Persistent `AUTH_EXPIRE` failures**
- WiFi connection times exploded from 4s to **328+ seconds** (or failed)
- Cascading BLE GATT connection timeouts

#### dev.82 — Revert to WIFI_PS_NONE (commit `61f7f754`)

```cpp
void WifiManager::applyPowerSave() {
    WiFi.setSleep(WIFI_PS_NONE);  // unconditional
}
```

Commit message rationale:
1. The hardware coexistence arbiter (`CONFIG_ESP_COEX_SW_COEXIST_ENABLE`)
   arbitrates radio access at MAC/PHY layer independently of power-save
2. Always-powered devices don't need battery savings
3. Modem sleep creates unacceptable timing jitter for WiFi auth frames

**15-minute soak test validation (dev.82):**

| Metric | Result |
|--------|--------|
| WiFi requests | 29/29 (100%), zero AUTH_EXPIRE |
| WiFi connect time | 4 seconds (was 328+s) |
| BLE connections | 7/8 (87.5%), 1 macOS CoreBT flake |
| BLE connect time | 4.5–15.8s (was 25+s or timeout) |
| Heap | Flat at 65.6 KB free |
| Coex failure logs | Zero |

#### dev.83 — BLE TX power reduction (Issue #239, 2026-09-26)

8-hour soak test revealed +20 dBm BLE TX caused 3 WiFi disconnections at
boot. Default lowered to +9 dBm (`CONFIG_BT_CTRL_DFT_TX_POWER_LEVEL_P9`).
At +9 dBm: zero disconnections, 2,200 GATT reads in 2 hours.

### The Fundamental Architectural Tension

The framework is caught on a razor's edge:

```
                   WIFI_PS_NONE            WIFI_PS_MIN_MODEM
                   ─────────────           ──────────────────
PREFER_WIFI     │  WiFi ✅ BLE ❌ (0x3e)   WiFi ❌ (AUTH_EXPIRE)  BLE ?
PREFER_BALANCE  │  WiFi ? BLE ?            WiFi ❌ (AUTH_EXPIRE)  BLE ?
PREFER_BT       │  WiFi ❌ (starved)       WiFi ❌                BLE ✅
```

- Any tilt toward WiFi (PS_NONE + PREFER_WIFI) starves BLE connection events
- Any tilt toward BLE breaks WiFi 802.11 auth (1s deadline)
- `PREFER_BALANCE` was tested and still failed WiFi auth

**What was NOT tested:** `PREFER_BALANCE` + `WIFI_PS_NONE`. The dev.78
test used `PREFER_BALANCE` alone (likely with the default power-save at
the time). The SmartSpin2k comparison shows this combination may work —
they run `WIFI_PS_NONE` + `PREFER_BALANCE` (default) successfully on the
original ESP32 with additional mitigations (BT controller modem sleep,
connection reattempt, paced WiFi reconnect).

## Step 0 — Desk Search: ESP-IDF / NimBLE 0x3e Issues

**Searched:** esp-idf, esp-nimble, h2zero/esp-nimble-cpp issues for `0x3e`,
`CONN_ESTABL_FAIL`, `status=574`, Pixel connection failures, WiFi coexistence.
13 relevant issues curated.

### Critical findings

**1. `WIFI_PS_NONE` is explicitly prohibited when BLE is active.**

ESP-IDF documentation and multiple issues confirm: with the shared 2.4 GHz
radio, `WIFI_PS_NONE` keeps the WiFi receiver continuously powered, depriving
the BLE controller of radio access. The WiFi driver logs:
```
E (1351) wifi:Error! Should enable WiFi modem sleep when both WiFi and Bluetooth are enabled!!!!!!
```
- [esp-idf#9595](https://github.com/espressif/esp-idf/issues/9595):
  `coex_enable()` crashes if `WIFI_PS_NONE` is set. Direct confirmation that
  the coex arbiter requires modem sleep to create idle slots for BLE.
- Required setting: `WIFI_PS_MIN_MODEM` (or `WIFI_PS_MAX_MODEM`).

**2. Direct precedent: 0x3e from modem sleep timing jitter.**

- [esp-idf#2467](https://github.com/espressif/esp-idf/issues/2467):
  10–15% BLE connection failure rate with reason `0x3e`. Cause: controller
  wake-up lead times caused the radio to miss the initial connection event
  window (6 × connInterval). Fixed via updated controller binary.

**3. Coex causes 0x3e on ESP32 family.**

- [esp-idf#11280](https://github.com/espressif/esp-idf/issues/11280):
  BLE connection fails in an endless loop when WiFi coex is active on
  ESP32-C3. Fixed via RF filter bandwidth patch (commit `e8dba71`,
  backported to v4.4, v5.1, master).
- [esp-idf#17871](https://github.com/espressif/esp-idf/issues/17871):
  ESP32-S3 WiFi+BLE coex — STA disconnects on Android 13+ hotspot only
  when BLE is active. **Open issue**, under investigation.

**4. Pixel-specific issues exist but are mostly pairing/encryption, not establishment.**

- [esp-idf#12948](https://github.com/espressif/esp-idf/issues/12948):
  Pixel 6a/7 GATT error 133 — legacy advertising incompatibility. Fix:
  extended advertising or connection parameter adjustment.
- [esp-idf#14959](https://github.com/espressif/esp-idf/issues/14959):
  Pixel 8 Pro NimBLE pairing problem — fixed in NimBLE security manager.
- [esp-idf#18126](https://github.com/espressif/esp-idf/issues/18126):
  Pixel 6a/7 MIC failure (0x3D) on reconnection — controller patch issued.

**5. NimBLE has a built-in connection reattempt feature.**

```ini
CONFIG_BT_NIMBLE_ENABLE_CONN_REATTEMPT=y
CONFIG_BT_NIMBLE_MAX_CONN_REATTEMPT=3
```
Auto-retries connection establishment on `0x3e` before reporting failure to
the application. This could mask the issue for centrals, but for peripherals
(our case) the central controls retry.

**6. Recommended coex-safe connection parameters.**

- Min interval: 24 units (30ms), max: 40 units (50ms)
- Supervision timeout: 400 units (4s)
- Avoid intervals < 20ms with concurrent WiFi
- NimBLE buffer increase: `CONFIG_BT_NIMBLE_MSYS1_BLOCK_COUNT=24` (from 12)

### Relevance to our failure

Our firmware runs `WIFI_PS_NONE` (confirmed in serial: `ps type: 0`). This
is the exact configuration ESP-IDF documents as incompatible with BLE. The
0x3e failure in the establishment window (post-CONNECT_IND, pre-first-data)
matches the pattern in esp-idf#2467 and esp-idf#11280. The Pixel fails
while the P12 tablet succeeds, likely because the Pixel's initial connection
parameters demand tighter radio scheduling that the starved controller cannot
service — but the actual parameters are unknown until Test C (HCI snoop).

### Comparative analysis: SmartSpin2k (shipping product, original ESP32)

[SmartSpin2k](https://github.com/doudar/SmartSpin2k) runs BLE FTMS server +
BLE HR/PM client + WiFi web UI simultaneously on the original ESP32 (less
capable than our S3). Research into their codebase reveals critical
configuration differences from our framework.

#### What SmartSpin2k does differently

| Setting | SmartSpin2k | Our Framework | Impact |
|---------|------------|---------------|--------|
| WiFi PS | `WIFI_PS_NONE` | `WIFI_PS_NONE` | Same |
| Coex preference | `PREFER_BALANCE` (default) | `PREFER_WIFI` (explicit) | **SS2K gives BLE equal priority** |
| BT controller modem sleep | `CONFIG_BTDM_CTRL_MODEM_SLEEP=y` | Not set | **SS2K's BT controller manages sleep/wake** |
| Connection reattempt | `CONFIG_BT_NIMBLE_ENABLE_CONN_REATTEMPT=y` (max 3) | Not set | **SS2K auto-retries on 0x3e** |
| Advertising interval | 100–156ms | 50ms (fixed) | SS2K wider, less RF contention |
| Supervision timeout (client) | 5000ms | — | Survives WiFi bursts |
| WiFi auto-reconnect | **Disabled** + paced retry (3×15s, 60s backoff) | Arduino default | **SS2K prevents RF starvation** |
| Scan duty cycle | ~67% (window=33, interval=49) | — | SS2K guarantees idle radio slots |
| Scan before connect | **Explicit stop + wait** | — | SS2K avoids scan/connect collision |
| MSYS2 block count | 24 blocks × 320B | Default (12) | More HCI buffer headroom |

#### Key insight: `PREFER_WIFI` vs `PREFER_BALANCE`

SmartSpin2k also runs `WIFI_PS_NONE` — yet it works. The **critical
difference** is the coex arbiter policy:

- Our framework forces `PREFER_WIFI` (comment in `sdkconfig.ble.defaults`
  §18: *"gives WiFi auth/assoc frames priority over BLE advertising events"*).
  Under `WIFI_PS_NONE`, this means WiFi **never** yields the radio.
- SmartSpin2k uses the default `PREFER_BALANCE`, which gives BLE and WiFi
  roughly equal radio time. Combined with BT controller modem sleep
  (`CONFIG_BTDM_CTRL_MODEM_SLEEP=y`), the BT controller can properly
  schedule its own wake-up windows for connection events.

This means our framework has **two compounding factors**:
1. `WIFI_PS_NONE` — WiFi radio never sleeps
2. `PREFER_WIFI` — WiFi always wins arbitration

Together, BLE connection events are starved. The Pixel's connection
establishment window (~6 × connInterval) expires because the controller
cannot service it.

#### SmartSpin2k's proven workarounds for 0x3e

From their [Issue #65](https://github.com/doudar/SmartSpin2k/issues/65)
(with `h2zero`, NimBLE author):

1. `CONFIG_BT_NIMBLE_ENABLE_CONN_REATTEMPT=y` + max 3 retries
2. Supervision timeout ≥ 5000ms on client connections
3. Scan duty cycle ~67% (never continuous)
4. Stop scanning before initiating connections
5. Disable WiFi auto-reconnect, pace retries

#### Note on ESP32 vs ESP32-S3 controller

The original ESP32 uses `CONFIG_BTDM_CTRL_*` (dual-mode Bluetooth
controller). The ESP32-S3 uses `CONFIG_BT_CTRL_*` (BLE-only controller).
Not all settings translate directly — the S3's controller binary is
different. However, the coex arbiter policy (`PREFER_BALANCE` vs
`PREFER_WIFI`) and NimBLE host-level settings (`CONN_REATTEMPT`) are
chip-independent.

## v1 Finding: BLE Depends on WiFi STA

**Observed:** BLE cannot operate without WiFi STA connected.

- **At boot:** No saved WiFi credentials → AP-only mode → `WiFi Station`
  precondition unsatisfied → `AppState` stays in `CONFIGURING` → BLE never
  initialises (BLEManager requires RUNNING state).
- **During operation:** Sustained STA loss while RUNNING regresses the app
  to CONFIGURING (`Application.cpp:471`, WiFi Station is a Startup
  precondition), where BLE reconnect and discovery are RUNNING-only
  (`BLEManager.cpp:~855`).

**Impact:** If the router goes down for >N seconds while the device is
relaying HR data via BLE, the relay stops and cannot restart until WiFi
recovers — even though the BLE link has no functional dependency on WiFi.

**Hardware verification:** (pending — power off router for 3 min while HR
strap is relaying, record app state and HR relay behaviour)

**Upstream issue:** (draft pending CA review — not yet filed)

## Summary / Root Cause Analysis

### Confirmed mechanism

The `0x3e` (`BLE_ERR_CONN_ESTABL_FAIL`) failure occurs in the BLE
connection **establishment window**: the ESP32-S3 controller receives the
Pixel's `CONNECT_IND`, enters the connection state, but cannot service the
first ~6 connection events because the WiFi radio holds the RF front-end.
The link-layer supervision timer expires before any data-channel packet is
exchanged.

### Two compounding factors

The framework's current configuration creates a coex dead zone:

1. **`WIFI_PS_NONE`** — WiFi radio receiver is continuously powered, never
   entering sleep states. The coex arbiter has no idle slots to allocate
   to BLE.

2. **`PREFER_WIFI`** (ESP-IDF default, enforced by D12) — WiFi always wins
   arbitration. When both WiFi and BLE need the radio simultaneously,
   BLE is deferred.

Together, the BLE controller is completely starved of radio time during the
time-critical connection establishment window. Devices with conservative
connection parameters (Lenovo Tab P12: 48.75ms interval, 5s timeout) have
enough tolerance to survive brief radio gaps. Devices with tighter
parameters (Pixel 10 Pro Fold — parameters unknown, pending HCI snoop)
exceed the starvation threshold and fail.

### Corroborating evidence

| Source | Finding |
|--------|---------|
| ESP-IDF documentation | `WIFI_PS_NONE` with BLE is explicitly prohibited |
| [esp-idf#9595](https://github.com/espressif/esp-idf/issues/9595) | `WIFI_PS_NONE` breaks the coex arbiter (crash) |
| [esp-idf#2467](https://github.com/espressif/esp-idf/issues/2467) | 10–15% BLE 0x3e failures from radio timing jitter |
| [esp-idf#11280](https://github.com/espressif/esp-idf/issues/11280) | Coex causes 0x3e connection loop on ESP32-C3 |
| [esp-idf#17871](https://github.com/espressif/esp-idf/issues/17871) | ESP32-S3 WiFi+BLE coex failure (open issue) |
| SmartSpin2k (shipping product) | Same stack, less capable hardware, works — different coex config |
| Serial log (`ps type: 0`) | Confirms `WIFI_PS_NONE` active |
| Serial log (`Coexist!!!`) | ESP-IDF warning about WiFi not yielding to BLE |

### The untested combination

The dev.73–dev.80 hardening cycle tested three coex configurations:

| Config | dev tag | WiFi PS (at time) | Result |
|--------|---------|-------------------|--------|
| `PREFER_BT` | dev.76 | unknown | WiFi starved, portal unreachable |
| `PREFER_BALANCE` | dev.78 | unknown (not `PS_NONE`) | `AUTH_EXPIRE` during 802.11 assoc |
| `PREFER_WIFI` (default) | dev.79 | then `PS_NONE` (dev.82) | WiFi ✅, BLE ❌ (0x3e on Pixel) |

**Critical gap:** `PREFER_BALANCE` + `WIFI_PS_NONE` was never tested together.

- The dev.78 test of `PREFER_BALANCE` likely ran with the ESP-IDF default
  power-save mode (not `WIFI_PS_NONE`), which would have introduced modem
  sleep timing jitter on top of the balanced arbitration — a double
  penalty for WiFi auth frames.

- SmartSpin2k proves that `PREFER_BALANCE` + `WIFI_PS_NONE` is viable on
  the original ESP32 (less capable than our S3). Their WiFi radio never
  sleeps (so auth frames aren't missed by sleep timing), but the arbiter
  gives BLE equal radio time (so connection events aren't starved).

- SmartSpin2k also layers additional mitigations that we lack:

  | Mitigation | SmartSpin2k | Our framework |
  |------------|------------|---------------|
  | `CONFIG_BT_NIMBLE_ENABLE_CONN_REATTEMPT=y` (max 3) | ✅ | ❌ |
  | BT controller modem sleep | ✅ | ❌ |
  | WiFi auto-reconnect disabled + paced retry | ✅ | ❌ |
  | Wider advertising interval (100–156ms) | ✅ | ❌ (50ms) |
  | Scan duty-cycle capping (~67%) | ✅ | ✅ (≤25/50%) |

### Framework applicability

If the fix is validated in Echenon (consumer app), the changes are entirely
in the **framework layer** — `WifiManager.cpp`, `sdkconfig.ble.defaults`,
and `BLEStack.cpp`. The fix should be upstreamed to `esp32-app-foundation`
so all consumer apps benefit. The D12 policy comment in `sdkconfig.ble.defaults`
and `BLEStack.cpp` will need updating to reflect the new evidence.

### Remaining hardware tests (Steps 1–6)

The research strongly implicates `PREFER_WIFI` + `WIFI_PS_NONE` as the root
cause. The remaining hardware tests should confirm this:

- **Step 2 (CONTROL)** is decisive: if the Pixel connects with WiFi off,
  coex is confirmed.
- **Test B** tests `WIFI_PS_MIN_MODEM` under the current `PREFER_WIFI` —
  but the SmartSpin2k evidence suggests the better experiment is
  `PREFER_BALANCE` + `WIFI_PS_NONE` (untested in our hardening cycle).
- **Test C (HCI snoop)** remains essential: the Pixel's actual connection
  parameters will reveal whether this is purely a coex timing issue or
  also an interop parameter issue.

### Escalation to Chief Architect

**Recommendation:** the CA should evaluate a revised coex policy that
incorporates the SmartSpin2k-proven approach. Suggested test matrix:

| # | WiFi PS | Coex Preference | Additional mitigations | Test |
|---|---------|----------------|----------------------|------|
| 1 | `WIFI_PS_NONE` | `PREFER_BALANCE` | None | Pixel ×10, WiFi auth ×10 |
| 2 | `WIFI_PS_NONE` | `PREFER_BALANCE` | + `CONN_REATTEMPT=y` (3) | Pixel ×10, WiFi auth ×10 |
| 3 | `WIFI_PS_NONE` | `PREFER_BALANCE` | + `CONN_REATTEMPT` + paced WiFi reconnect | Pixel ×10, WiFi auth ×10, 15-min soak |

The critical question the dev.78 test left unanswered: **does `PREFER_BALANCE`
still cause `AUTH_EXPIRE` when WiFi power-save is explicitly `WIFI_PS_NONE`
(radio always on)?** SmartSpin2k's evidence says no — but they're on the
original ESP32, not the S3. Hardware validation on our board is required.

**This document does NOT recommend a coex architecture option.** It presents
the evidence and the untested gap for CA decision.
