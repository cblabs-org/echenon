## Test A — WiFi STA Disconnected (Designed) / Baseline Comparison (Actual)

### Design

Disconnect WiFi STA so the 2.4 GHz coexistence arbiter is not contending
with WiFi, then test whether the Android phone can connect.

### Actual execution

**Test A as designed was blocked.** When WiFi credentials are removed, the
framework enters AP-only mode and the `WiFi Station` precondition (cause=8,
severity=3) prevents `AppState::Running`. BLE init is gated behind RUNNING
state, so BLE never starts without a STA connection.

Serial evidence (AP-only boot):
```
I (2994) WifiManager: softAP('esp32-device') returned true
I (3281) Application: Precondition unsatisfied: WiFi Station (cause=8, severity=3)
  ... (repeats every 500ms, BLE never initialises)
```

> **Side-finding:** The softAP SSID uses the generic `esp32-device` instead of
> the app-configured hostname. Filed as
> [esp32-app-foundation#294](https://github.com/matthewmcneill/esp32-app-foundation/issues/294).

> **v1 finding: BLE depends on WiFi STA.** BLE cannot operate without WiFi STA.
> At boot, no STA → no RUNNING → no BLE. If STA is lost while RUNNING, the app
> regresses to CONFIGURING (`Application.cpp:471`), where BLE reconnect and
> discovery are blocked (RUNNING-only gates in `BLEManager.cpp:~855`). This
> means sustained router outage kills BLE relay even though BLE has no
> dependency on WiFi. See [v1 Finding](#v1-finding--ble-depends-on-wifi-sta)
> section below.

No `Central connected` log — the connection fails during the establishment

events, causing `BLE_ERR_CONN_ESTABL_FAIL`.

### Analysis

1. **The phone is the only device that fails.** Mac and tablet connect
   reliably under identical conditions.

2. **The tablet's negotiated connection parameters** are more conservative
   than the Mac's (48.75ms interval vs 30ms; 5000ms supervision timeout
   vs 720ms). Both succeed.

3. **The phone's requested connection parameters are unknown** — the
   connection fails before the host stack logs them. HCI snoop log
   (Test C) is required to determine what the phone requested.

4. **The 0x3e failure occurs in the establishment window**, after
   `CONNECT_IND` is received. The ESP32 enters the connection but cannot
   service the first connection events — consistent with the coex arbiter
   under `WIFI_PS_NONE` not yielding WiFi radio time for BLE connection
   event servicing.

### Conclusion

Test A (WiFi off) was not executed due to the framework's BLE-requires-RUNNING
gate. The baseline comparison shows the phone fails while Mac and tablet
succeed under identical conditions. The failure is in the connection
establishment window (post-CONNECT_IND), consistent with coex starvation.
The phone's actual requested parameters are not yet known — Test C (HCI snoop)
is essential.

## Framework Coexistence Decision History

Reconstructed from PA memory files, workorders (`pr-225-ble-manager`),
source code comments, and commit messages. This is the complete record of
how the framework arrived at its current coex configuration. Note: the
comments say "PREFER_WIFI" but the actual ESP-IDF default is
`PREFER_BALANCE` — see [C1 correction](#c1-correction-the-framework-already-runs-prefer_balance).

### Timeline

#### dev.67 — First coex anomaly (WO-6 hardware acceptance, 2026-09-23)

During rapid BLE connection/disconnection cycling (3 cycles), WiFi
disconnected and fell back to AP mode:
```
wifi:Coexist: Wi-Fi connect fail, apply reconnect coex policy
```
Identified as an ESP-IDF radio coexistence limitation under connection
churn, not a logic defect.

#### dev.73–dev.80 — Radio hardening cycle (2026-09-25)

Two simultaneous failures during bench testing drove experiments:
- Android BLE connections dropped with GATT CONN TIMEOUT (Error 147/133)
- WiFi dropped with `AUTH_EXPIRE` (reason 2)

**Experiment 1: `PREFER_BT` (dev.76, commit `22882ffc`)**
- Set `esp_coex_preference_set(ESP_COEX_PREFER_BT)`
- **Result: WiFi completely starved** — HTTP portal unreachable.

**Experiment 2: `PREFER_BALANCE` (dev.78, commit `651b6eef`)**
- Set `esp_coex_preference_set(ESP_COEX_PREFER_BALANCE)`
- **Result: still caused `AUTH_EXPIRE`** during 802.11 association.
- 802.11 auth/assoc frames have a hard 1-second deadline; balanced
  time-sharing caused the WiFi radio to miss these frames.

**Decision D12: revert to `PREFER_WIFI` (dev.79, commit `7521972f`)**
- Removed `esp_coex_preference_set()` entirely, falling back to the
  ESP-IDF default (`PREFER_WIFI`, enum 0).
- WiFi auth/assoc frames granted strict arbitration priority.
- BLE stability achieved through other mechanisms:
  - Deferred connection parameter negotiation (no immediate
    `updateConnParams()` on `PeerConnected`)
  - Supervision timeout elongation (4.0s after MTU exchange)
- **This decision was codified as permanent policy:**

Source: `sdkconfig.ble.defaults` L302–315:
```ini
# IMPORTANT — do NOT call esp_coex_preference_set() in application code:
#   - PREFER_BT (dev.76):      Starved WiFi entirely — portal unreachable.
#   - PREFER_BALANCE (dev.78):  Still caused AUTH_EXPIRE during WiFi 802.11
#                               association (auth frames have a 1s deadline).
#   - Default / PREFER_WIFI:    Works reliably.  BLE stability comes from
#                               +20 dBm TX power and deferred connection
#                               parameter updates, not from coexistence tuning.
```

Source: `BLEStack.cpp` L270–273:
```cpp
// Wi-Fi / BLE coexistence: leave at ESP-IDF default (PREFER_WIFI, enum 0).
// PREFER_BT (dev.76) starved WiFi entirely; PREFER_BALANCE (dev.78) still
// caused AUTH_EXPIRE during WiFi association.
```

**STA timeout extension (dev.80, commit `1f1dd207`):**
- `STA_ATTEMPT_TIMEOUT_MS` increased from 15s → 30s to allow 802.11
  auth retry cycles (8–10s on congested 2.4 GHz) plus DHCP.

#### dev.81 — WO-10 / WIFI_PS_MIN_MODEM trial (2026-09-25)

Issue #236 addressed WiFi STA resilience. WO-10 mandated Decision **D-E**:
```cpp
void WifiManager::applyPowerSave() {
#if !defined(UNIT_TEST) && (defined(WITH_BLE) || ...)
    WiFi.setSleep(WIFI_PS_MIN_MODEM);
#else
    WiFi.setSleep(WIFI_PS_NONE);
#endif
}
```

**Rationale:** ESP-IDF logged *"Should enable WiFi modem sleep when both
WiFi and Bluetooth are enabled"*, and modem sleep was believed necessary
to yield the radio to BLE.

**The dev.81 regression:** On congested 2.4 GHz networks:
- Modem sleep caused WiFi radio to enter sleep states during 802.11 auth
  handshakes, sleeping through auth response frames
- **Persistent `AUTH_EXPIRE` failures**
- WiFi connection times exploded from 4s to **328+ seconds** (or failed)
- Cascading BLE GATT connection timeouts

#### dev.82 — Revert to WIFI_PS_NONE (commit `61f7f754`)

```cpp
void WifiManager::applyPowerSave() {
    WiFi.setSleep(WIFI_PS_NONE);  // unconditional
}
```

Commit message rationale:
1. The hardware coexistence arbiter (`CONFIG_ESP_COEX_SW_COEXIST_ENABLE`)
   arbitrates radio access at MAC/PHY layer independently of power-save
2. Always-powered devices don't need battery savings
3. Modem sleep creates unacceptable timing jitter for WiFi auth frames

**15-minute soak test validation (dev.82):**

| Metric | Result |
|--------|--------|
| WiFi requests | 29/29 (100%), zero AUTH_EXPIRE |
| WiFi connect time | 4 seconds (was 328+s) |
| BLE connections | 7/8 (87.5%), 1 macOS CoreBT flake |
| BLE connect time | 4.5–15.8s (was 25+s or timeout) |
| Heap | Flat at 65.6 KB free |
| Coex failure logs | Zero |

#### dev.83 — BLE TX power reduction (Issue #239, 2026-09-26)

8-hour soak test revealed +20 dBm BLE TX caused 3 WiFi disconnections at
boot. Default lowered to +9 dBm (`CONFIG_BT_CTRL_DFT_TX_POWER_LEVEL_P9`).
At +9 dBm: zero disconnections, 2,200 GATT reads in 2 hours.

### C1 correction: the framework already runs PREFER_BALANCE

> **CORRECTION (CA review 2026-10-13):** The earlier analysis identified
> `PREFER_WIFI` as a compounding factor. This was wrong.

**Evidence:**
- ESP-IDF 5.5.5 `esp_coexist.h` L115–126: `esp_coex_preference_set()` is
  `@deprecated`. Doc comment: *"Default, it prefer to balance."*
- `grep -rn esp_coex_preference_set framework/modules src` → **no calls**
  in our codebase.

The framework's coex arbiter runs the ESP-IDF default: **`PREFER_BALANCE`**,
not `PREFER_WIFI`. The comments in `BLEStack.cpp` L270–273 and
`sdkconfig.ble.defaults` L302–315 that say "PREFER_WIFI (enum 0)" are
**wrong** — the enum value 0 maps to `ESP_COEX_PREFER_BALANCE` in current
ESP-IDF, not `PREFER_WIFI`.

This means `PREFER_BALANCE` + `WIFI_PS_NONE` **IS the current, failing
configuration**. The "untested combination" hypothesis from the earlier
analysis is invalidated — we are already running it and the Pixel still
fails.

> **Finding (C1): The framework comments in `BLEStack.cpp` and
> `sdkconfig.ble.defaults` incorrectly label the coex default as
> `PREFER_WIFI`. These should be corrected. The deprecated
> `esp_coex_preference_set()` API should not be used.**
> Draft upstream issue (i) covers this.

### Revised analysis: what differs from SmartSpin2k?

With `PREFER_BALANCE` + `WIFI_PS_NONE` the same on both sides, the
failure must come from elsewhere. Candidates:

1. **Chip/controller:** SmartSpin2k runs the classic ESP32 (dual-core
   Xtensa LX6 with dual-mode BT controller: `CONFIG_BTDM_CTRL_*`). We
   run the ESP32-S3 (dual-core LX7 with BLE-only controller:
   `CONFIG_BT_CTRL_*`). Different controller binaries, different RF
   arbitration behaviour.
2. **ESP-IDF version:** SmartSpin2k uses ESP-IDF 5.4.2. We use 5.5.5.
   Controller binary and coex arbiter may differ.
3. **WiFi traffic during tests:** Our diag build has the dashboard
   polling `/api/echenon/live` (HTTP requests during BLE connection
   attempts) and mDNS announcements. SmartSpin2k's web UI is passive
   (no polling unless a browser is open).
4. **Diag build ISR/CPU load:** `WITH_SIGNAL_LOGGER` runs ADC DMA with
   interrupt processing. This contends with the BLE controller on
   Core 0.
5. **WiFi auto-reconnect:** SmartSpin2k disables Arduino auto-reconnect
   and paces retries. Our framework uses Arduino's default (aggressive
   reconnect loops on AP loss).

## Step 0 — Desk Search: ESP-IDF / NimBLE 0x3e Issues

**Searched:** esp-idf, esp-nimble, h2zero/esp-nimble-cpp issues for `0x3e`,
`CONN_ESTABL_FAIL`, `status=574`, Pixel connection failures, WiFi coexistence.
13 relevant issues curated.

### Critical findings

**1. `WIFI_PS_NONE` is explicitly prohibited when BLE is active.**

ESP-IDF documentation and multiple issues confirm: with the shared 2.4 GHz
radio, `WIFI_PS_NONE` keeps the WiFi receiver continuously powered, depriving
the BLE controller of radio access. The WiFi driver logs:
```
E (1351) wifi:Error! Should enable WiFi modem sleep when both WiFi and Bluetooth are enabled!!!!!!
```
- [esp-idf#9595](https://github.com/espressif/esp-idf/issues/9595):
  `coex_enable()` crashes if `WIFI_PS_NONE` is set. Direct confirmation that
  the coex arbiter requires modem sleep to create idle slots for BLE.
- Required setting: `WIFI_PS_MIN_MODEM` (or `WIFI_PS_MAX_MODEM`).

**2. Direct precedent: 0x3e from modem sleep timing jitter.**

- [esp-idf#2467](https://github.com/espressif/esp-idf/issues/2467):
  10–15% BLE connection failure rate with reason `0x3e`. Cause: controller
  wake-up lead times caused the radio to miss the initial connection event
  window (6 × connInterval). Fixed via updated controller binary.

**3. Coex causes 0x3e on ESP32 family.**

- [esp-idf#11280](https://github.com/espressif/esp-idf/issues/11280):
  BLE connection fails in an endless loop when WiFi coex is active on
  ESP32-C3. Fixed via RF filter bandwidth patch (commit `e8dba71`,
  backported to v4.4, v5.1, master).
- [esp-idf#17871](https://github.com/espressif/esp-idf/issues/17871):
  ESP32-S3 WiFi+BLE coex — STA disconnects on Android 13+ hotspot only
  when BLE is active. **Open issue**, under investigation.

**4. Pixel-specific issues exist but are mostly pairing/encryption, not establishment.**

- [esp-idf#12948](https://github.com/espressif/esp-idf/issues/12948):
  Pixel 6a/7 GATT error 133 — legacy advertising incompatibility. Fix:
  extended advertising or connection parameter adjustment.
- [esp-idf#14959](https://github.com/espressif/esp-idf/issues/14959):
  Pixel 8 Pro NimBLE pairing problem — fixed in NimBLE security manager.
- [esp-idf#18126](https://github.com/espressif/esp-idf/issues/18126):
  Pixel 6a/7 MIC failure (0x3D) on reconnection — controller patch issued.

**5. NimBLE has a built-in connection reattempt feature.**

```ini
CONFIG_BT_NIMBLE_ENABLE_CONN_REATTEMPT=y
CONFIG_BT_NIMBLE_MAX_CONN_REATTEMPT=3
```
Auto-retries connection establishment on `0x3e` before reporting failure to
the application. This could mask the issue for centrals, but for peripherals
(our case) the central controls retry.

**6. Recommended coex-safe connection parameters.**

- Min interval: 24 units (30ms), max: 40 units (50ms)
- Supervision timeout: 400 units (4s)
- Avoid intervals < 20ms with concurrent WiFi
- NimBLE buffer increase: `CONFIG_BT_NIMBLE_MSYS1_BLOCK_COUNT=24` (from 12)

### Relevance to our failure

Our firmware runs `WIFI_PS_NONE` (confirmed in serial: `ps type: 0`). This
is the exact configuration ESP-IDF documents as incompatible with BLE. The
0x3e failure in the establishment window (post-CONNECT_IND, pre-first-data)
matches the pattern in esp-idf#2467 and esp-idf#11280. The Pixel fails
while the P12 tablet succeeds, likely because the Pixel's initial connection
parameters demand tighter radio scheduling that the starved controller cannot
service — but the actual parameters are unknown until Test C (HCI snoop).

### Comparative analysis: SmartSpin2k (shipping product, original ESP32)

[SmartSpin2k](https://github.com/doudar/SmartSpin2k) runs BLE FTMS server +
BLE HR/PM client + WiFi web UI simultaneously on the original ESP32 (less
capable than our S3). Research into their codebase reveals critical
configuration differences from our framework.

#### What SmartSpin2k does differently

| Setting | SmartSpin2k | Our Framework | Same? |
|---------|------------|---------------|-------|
| WiFi PS | `WIFI_PS_NONE` | `WIFI_PS_NONE` | ✅ Same |
| Coex preference | `PREFER_BALANCE` (default) | `PREFER_BALANCE` (default) | ✅ Same (C1) |
| Connection reattempt | `CONFIG_BT_NIMBLE_ENABLE_CONN_REATTEMPT=y` (max 3) | Enabled by default on ESP32-S3 | ✅ Same (C2) |
| BT controller modem sleep | `CONFIG_BTDM_CTRL_MODEM_SLEEP=y` | `# CONFIG_BT_CTRL_MODEM_SLEEP is not set` | Different — but see C3 |
| Advertising interval | 100–156ms | 50ms (fixed) | **Different** |
| Supervision timeout (client) | 5000ms | — | **Different** |
| WiFi auto-reconnect | **Disabled** + paced retry (3×15s, 60s backoff) | Arduino default | **Different** |
| Scan duty cycle | ~67% (window=33, interval=49) | — | **Different** |
| Scan before connect | **Explicit stop + wait** | — | **Different** |
| MSYS2 block count | 24 blocks × 320B | Default (12) | **Different** |
| Chip | Classic ESP32 (BTDM controller) | ESP32-S3 (BLE-only controller) | **Different** |
| ESP-IDF | 5.4.2 | 5.5.5 | **Different** |

> **C2 correction:** `CONFIG_BT_NIMBLE_ENABLE_CONN_REATTEMPT` defaults to
> `y` on ESP32-S3 per Kconfig (`default y if IDF_TARGET_ESP32S3`). The
> serial log's "Reattempt advertising; reason: 0x3e" IS this feature in
> action — on the peripheral side it restarts advertising after a failed
> connection. It cannot fix a central-side establishment failure.

> **C3 correction:** BT controller modem sleep should NOT be adopted.
> [espressif/esp-idf#2467](https://github.com/espressif/esp-idf/issues/2467)
> (cited in Step 0) is titled "LE Connection fail rate 10–15% after
> enabling BT Modem sleep". Our build correctly has
> `# CONFIG_BT_CTRL_MODEM_SLEEP is not set` (mains-powered device).

#### Revised key insight: coex preference is NOT the differentiator

The earlier analysis identified `PREFER_WIFI` vs `PREFER_BALANCE` as the
key difference. **This was wrong** (C1). Both projects run `PREFER_BALANCE`.
Both run `WIFI_PS_NONE`. Both have connection reattempt enabled (C2).

The actual differences that may explain SmartSpin2k's success are:
- **Different chip/controller** (classic ESP32 vs ESP32-S3)
- **Different ESP-IDF version** (5.4.2 vs 5.5.5)
- **No WiFi traffic during BLE connection** (passive web UI)
- **No ISR/DMA load** (no signal logger)
- **Wider advertising intervals** (100–156ms vs 50ms)
- **WiFi auto-reconnect disabled** with paced retry

#### SmartSpin2k's proven workarounds for 0x3e

From their [Issue #65](https://github.com/doudar/SmartSpin2k/issues/65)
(with `h2zero`, NimBLE author):

1. `CONFIG_BT_NIMBLE_ENABLE_CONN_REATTEMPT=y` + max 3 retries
2. Supervision timeout ≥ 5000ms on client connections
3. Scan duty cycle ~67% (never continuous)
4. Stop scanning before initiating connections
5. Disable WiFi auto-reconnect, pace retries

#### Note on ESP32 vs ESP32-S3 controller

The original ESP32 uses `CONFIG_BTDM_CTRL_*` (dual-mode Bluetooth
controller). The ESP32-S3 uses `CONFIG_BT_CTRL_*` (BLE-only controller).
Not all settings translate directly — the S3's controller binary is
different. However, the coex arbiter policy (both use `PREFER_BALANCE`)
and NimBLE host-level settings (`CONN_REATTEMPT`) are
chip-independent.

### Critical Finding: Cold-Start Connection Failure Pattern

**After flashing v0.1.0-dev.10** (DEBUG BLE logging, ~10 min gap), the nRF
Connect log reveals a different pattern:

| Attempt | Time | Status | Error |
|---------|------|--------|-------|
| 1 | 23:21:15 | ❌ FAIL | Error 147 (0x93): GATT_CONN_TIMEOUT after 448 ms |
| 2 | 23:21:17 | ❌ FAIL | Error 147 (0x93): GATT_CONN_TIMEOUT after 386 ms |
| 3 | 23:21:19 | ❌ FAIL | Error 147 (0x93): GATT_CONN_TIMEOUT after 448 ms |
| 4 | 23:21:20 | ✅ PASS | Connected in 101 ms |

Each failed attempt also generated Error 133 (0x85): GATT ERROR as a secondary
callback. The ESP32 serial log showed **no connection events** for the 3 failed
attempts — the controller did not process the `CONNECT_IND` at all.

**Similar pattern observed with the Echelon app on v0.1.0-dev.9:**
- First connection attempt: had to "spam" the connect button 3× before success
- Second connection (after disconnect): had to spam 5–6× before success
- Once connected: stable, HR notifications flowed at 1/sec, MTU 185

**Emerging hypothesis: cold-start / idle-state connection failure**

The consistent pattern across both firmware builds and both apps:

> After a period with no BLE connection activity (just advertising + WiFi STA),
> the first 1–4 connection attempts fail. The phone sends `CONNECT_IND` but the
> ESP32 controller does not respond within the connection establishment window.
> Once one connection succeeds, subsequent connections work reliably (12/12 in
> rapid cycling).

This suggests the failure is not about connection *parameters* or *interop*
but about the **coex arbiter's radio scheduling state when BLE has been
advertising-only for an extended period**. Possible mechanisms:

1. **Coex priority demotion during advertising-only**: The arbiter may assign
   lower priority to BLE advertising events than to WiFi, since advertising
   is tolerant of missed events. When a `CONNECT_IND` arrives, the controller
   needs to respond within 1.25 ms on the next connection event — but if the
   arbiter has given that slot to WiFi, the response is missed.

2. **Controller idle-state latency**: The BLE controller may reduce its
   scanning of advertising channels when no connections are active, increasing
   the latency to detect and process a `CONNECT_IND`.

3. **WiFi beacon/DTIM collision**: With `WIFI_PS_NONE` the radio never sleeps,
   and beacon reception every ~100 ms creates periodic windows where BLE is
   blocked. The probability of collision with the narrow `CONNECT_IND` window
   increases with longer idle periods (no BLE connection events to "train" the
   scheduler).

4. **First-connection priority boost**: Once the controller successfully
   establishes a connection, the coex arbiter may boost BLE priority for
   subsequent connection events. This would explain the 100% success rate
   in rapid cycling after the first success.

## ESP-IDF Source Code Analysis: Cold-Start Mechanism (2026-10-13)

Research into the ESP-IDF 5.5.5 source code for the ESP32-S3 confirms that the
cold-start connection failure is caused by a **collision between three
independent mechanisms** under `WIFI_PS_NONE` + `PREFER_BALANCE`:

### Mechanism 1: RF monopoly under `WIFI_PS_NONE`

- `WIFI_PS_MIN_MODEM` sleeps between AP beacons, opening 90–95ms idle windows
  for BLE to use the RF uncontested.
- `WIFI_PS_NONE` keeps the WiFi receiver and RF synthesiser continuously
  energised. BLE must fight for every microsecond via the software coex arbiter
  (`libcoexist.a`).

### Mechanism 2: Advertising has lowest priority in the controller

From the RivieraWaves IP ROM data table (`rwip_priority` at `0x3ff1eea8` in
`components/esp_rom/esp32s3/ld/esp32s3.rom.ld` L917):

| Link type | Base priority | Increment |
|-----------|---------------|-----------|
| Advertising (`adv`) | `0x05` | `0x01` — **lowest** |
| Active connection (`con`) | `0x0E`–`0x10` | `0x01` |

Until a connection is **anchored and validated** (first data packet exchanged),
the coex arbiter does NOT treat the link as a protected connection.

### Mechanism 3: Dynamic priority escalation is DISABLED on ESP32-S3

In `components/bt/controller/esp32c3/bt.c` L474:

```c
static const struct osi_funcs_t osi_funcs_ro = {
    ...
    ._coex_core_ble_conn_dyn_prio_get = NULL,  // <--- Explicitly NULL
    ...
};
```

The controller does **not** dynamically escalate coex priority during connection
setup. Priority is determined strictly by static tables until the connection
state machine transitions to `ESTABLISHED`.

### Consequence: the 6-event establishment deadline

From `components/bt/host/nimble/nimble/nimble/controller/src/ble_ll_conn.c`
L3015–3027:

```c
if (connsm->conn_state == BLE_LL_CONN_STATE_CREATED) {
    tmo = (uint32_t)connsm->conn_itvl * BLE_LL_CONN_ITVL_USECS * 6UL;
    ble_err = BLE_ERR_CONN_ESTABLISHMENT; // 0x3e
} else {
    tmo = connsm->supervision_tmo * BLE_HCI_CONN_SPVN_TMO_UNITS * 1000UL;
    ble_err = BLE_ERR_CONN_SPVN_TMO;
}
```

- **Exactly 6 connection events** to establish the link (Bluetooth Core Spec
  Vol 6, Part B, §4.5.2)
- This is **independent** of the 5000ms supervision timeout (which only applies
  after `BLE_LL_CONN_STATE_ESTABLISHED`)
- With `conn_itvl = 15` (18.75ms, as the Pixel negotiates): timeout =
  6 × 18.75ms = **112.5ms**
- If WiFi holds the radio for just 113ms during those 6 events → `0x3e`
  guaranteed on the peripheral, `GATT_CONN_TIMEOUT` on the phone

### Why subsequent connections succeed

Once a connection is established:
1. The controller's RF synthesiser, AGC, and low-power clock calibration
   (`btdm_lpcycle_us`) remain locked and warm
2. Coex state transitions activate BLE dynamic priority for connection events
3. The arbiter learns to protect BLE connection event windows

Rapid reconnects hit an already-warmed controller. A 10-minute idle drops the
controller back into modem sleep with drifted calibration and WiFi dominance.

### Controller idle-state wake-up latency

From `components/bt/controller/esp32c3/bt.c`:

```c
#define BTDM_MIN_SLEEP_DURATION     (24) // 7.5 ms
#define BTDM_MODEM_WAKE_UP_DELAY    (8)  // 2.5 ms
```

When advertising-only, the controller enters modem sleep between advertising
events: MAC and Baseband powered down, RF synthesiser PLL shut down. Wake-up
requires 2.5ms to restart PLL and calibrate the slow clock. After 10 minutes
idle, clock drift increases, making the 150µs `T_IFS` window after `ADV_IND`
harder to hit.

### Runtime observability

- No public coex grant/denial counters in the C API
- `CONFIG_ESP_COEX_GPIO_DEBUG=y` routes internal coex signals to GPIO pins for
  logic analyser capture
- `CONFIG_BT_CTRL_LE_LOG_EN=y` logs internal controller scheduling events
- `coex_status_get(bitmap)` returns current WiFi/BLE/BT active status flags

## v1 Finding: BLE Depends on WiFi STA

**Observed:** BLE cannot operate without WiFi STA connected.

- **At boot:** No saved WiFi credentials → AP-only mode → `WiFi Station`
  precondition unsatisfied → `AppState` stays in `CONFIGURING` → BLE never
  initialises (BLEManager requires RUNNING state).
- **During operation:** Sustained STA loss while RUNNING regresses the app
  to CONFIGURING (`Application.cpp:471`, WiFi Station is a Startup
  precondition), where BLE reconnect and discovery are RUNNING-only
  (`BLEManager.cpp:~855`).

**Impact:** If the router goes down for >N seconds while the device is
relaying HR data via BLE, the relay stops and cannot restart until WiFi
recovers — even though the BLE link has no functional dependency on WiFi.

strap is relaying, record app state and HR relay behaviour)

## Summary / Root Cause Analysis

### Leading hypothesis

> **C4 correction:** `WIFI_PS_NONE` is the leading suspect, not a confirmed
> cause. [espressif/esp-idf#9595](https://github.com/espressif/esp-idf/issues/9595)
> was a crash bug that Espressif fixed — it does not prove PS_NONE is
> prohibited. The serial log's `"Coexist!!! Wi-Fi station would only keep
> waked when available"` suggests the coex scheduler still time-slices
> under PS_NONE, but with reduced BLE radio time.

The `0x3e` (`BLE_ERR_CONN_ESTABL_FAIL`) failure occurs in the BLE
connection **establishment window**: the ESP32-S3 controller receives the
Pixel's `CONNECT_IND`, enters the connection state, but fails to service
the first ~6 connection events. The link-layer supervision timer expires
before any data-channel packet is exchanged.

### Leading suspect: `WIFI_PS_NONE` + advertising-only idle state

The framework's `WifiManager::applyPowerSave()` forces `WIFI_PS_NONE`.
Source code research (see [ESP-IDF Source Code Analysis](#esp-idf-source-code-analysis-cold-start-mechanism-2026-10-13))
confirms this creates a three-way collision:

1. **WiFi monopolises the RF** under `PS_NONE` (no idle windows for BLE)
2. **Advertising has lowest coex priority** (`0x05` vs `0x0E+` for connections)
3. **Dynamic priority escalation is disabled** on ESP32-S3
   (`_coex_core_ble_conn_dyn_prio_get = NULL`)

The establishment window is exactly 6 × `conn_itvl`. With the Pixel's
18.75ms interval, this gives only **112.5ms** to exchange the first packet.
WiFi under `PS_NONE` easily monopolises this window when the controller's
RF subsystem is cold (PLL off, clock drifted after idle).
